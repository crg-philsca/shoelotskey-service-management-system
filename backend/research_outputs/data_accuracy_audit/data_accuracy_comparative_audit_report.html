1. Audit Methodology, Criteria & Operational Definitions

Strict Read-Only Verification Mandate: In accordance with Capstone Project 2 empirical integrity directives, this audit performed zero data modifications, insertions, or deletions. No manuscript claims were accepted a priori; each metric is derived directly from the physical rows of shoelotskey.db and its persistent audit trail in audit_logs.

A. Duplicate Transaction Criteria

A record is classified as a duplicate if either:

  • Key Collision: Multiple rows sharing identical order_id or order_number.
  • Semantic Double-Submission: Multiple rows having the identical customer name, intake date (YYYY-MM-DD), grand total, and service items entered consecutively.

B. Incomplete Record Criteria

An incomplete transaction is defined as any job order lacking any mandatory field necessary for processing:

  • Missing or blank order_number, customer_name, or contact_number.
  • Missing foreign key reference (status_id or priority_id).
  • Zero associated items in the child items table (orphaned job order).
  • Missing or non-positive grand_total (≤ 0.00).
  • Missing creation timestamp (created_at).

C. Data Correction vs. Routine Workflow

To avoid inflating error rates with normal shop operations, system audit logs were parsed under strict distinction:

  • Excluded as Routine Lifecycle Updates: Status transitions (New Order → On-going → For Release → Claimed), automated inventory deduction flags (inventory_applied = 1), automated ML inference logging, payment collections on pickup, and shop delivery rescheduling.
  • Counted as Actual Data Corrections: Clerical edits modifying customer name, altering shoe condition inspection notes, rectifying pricing errors, or altering intake specifications after creation.

Authoritative SQL Audit Query

-- Comprehensive extraction of all digital orders with relational integrity joins
SELECT 
    o.order_id,
    o.order_number,
    c.customer_name,
    c.contact_number,
    s.status_name,
    p.priority_name,
    o.grand_total,
    o.created_at,
    COUNT(i.item_id) AS items_count,
    pay.method_id,
    pay.status_id AS payment_status_id,
    d.pref_id AS shipping_pref_id
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
LEFT JOIN status s ON o.status_id = s.status_id
LEFT JOIN priority_levels p ON o.priority_id = p.priority_id
LEFT JOIN items i ON o.order_id = i.order_id
LEFT JOIN payments pay ON o.order_id = pay.order_id
LEFT JOIN deliveries d ON o.order_id = d.order_id
GROUP BY o.order_id
ORDER BY o.order_id ASC;
