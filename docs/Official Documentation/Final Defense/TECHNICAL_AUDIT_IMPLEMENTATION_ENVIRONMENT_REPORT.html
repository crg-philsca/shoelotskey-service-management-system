💡 SemVer Notation Guide: What Does the Caret (^) Symbol Mean?

In software package manifests (package.json), the caret symbol (^) is standard Semantic Versioning (SemVer) notation:

  • ^5.9.3 (Caret Range): Instructs npm to accept any compatible minor or patch update up to, but not including, the next major version (i.e. ≥ 5.9.3 and < 6.0.0).
  • ^6.4.1 $ ightarrow$ Resolved to 6.4.3: The caret permitted Vite to install safe patch 6.4.3 in package-lock.json.
  • 18.3.1 (No Caret): Denotes an exact pin. No automatic upgrades were permitted.
  • For Defense Inquiries: The "Lockfile Version" is the definitive, locked number to cite for defense questions, while "Declared Constraint" records the range specified in the developer manifest.

Section 3.9 Overview & Three-Tier Architecture
### 3.9 Implementation Environment and Technology Stack The Shoelotskey Service Management System was deployed as a modular, three-tier cloud-based web application comprising a presentation layer, an application and predictive service layer, and a relational data persistence layer. To document operational reproducibility, dependencies and runtime configurations were verified across four formal levels: declared manifest constraints, lockfile-resolved dependency versions, locally installed development packages, and verified cloud production configurations. Historical evaluation milestones—specifically the formal shop pilot implementation (September 2–16, 2026) and evaluator testing (September 17–22, 2026)—were analyzed against repository release records and live cloud deployment telemetry.
Section 3.9.1 Presentation Layer Architecture
#### 3.9.1 Presentation Layer Architecture The client interface was developed as a responsive Single-Page Application (SPA) utilizing React (version 18.3.1) and React DOM (version 18.3.1), with static type checking enforced via TypeScript (version 5.9.3) targeting the ECMAScript 2020 standard. Client-side routing was governed by React Router DOM (version 7.18.2). Interface styling was implemented through Tailwind CSS (version 4.1.12) integrated via the native @tailwindcss/vite plugin architecture. Build compilation and asset optimization were executed using Vite (version 6.4.3). Managerial reporting visualizations were rendered using Recharts (version 2.15.2), vector iconography was supplied by Lucide React (version 0.487.0), and client-to-server communication was conducted asynchronously through Axios (version 1.19.0) with date manipulation handled via date-fns (version 3.6.0). In production, the single-page application was compiled via the heroku-postbuild lifecycle hook into static bundles served by FastAPI's StaticFiles and catch-all pushState routing.
Section 3.9.2 Application and Predictive Service Layer
#### 3.9.2 Application and Predictive Service Layer The server-side application was developed using FastAPI (declared constraint >=0.115.0; version 0.135.1 in the active development environment), an asynchronous Python web framework built upon Starlette and Pydantic (version 2.12.5). In cloud production, the application was hosted on the Heroku-24 stack (Ubuntu 24.04 LTS) executing Python (runtime version 3.12 specified in .python-version). Server process supervision was governed by Gunicorn executing Uvicorn ASGI workers through the configured entrypoint: gunicorn -w 1 -k uvicorn.workers.UvicornWorker --chdir backend main:app. The selection of a single worker process was specifically configured to operate deterministically within the 512 MB memory boundary of the cloud Basic dyno tier, utilizing FastAPI's asynchronous event loop to handle concurrent non-blocking requests without triggering memory quota exhaustion. Predictive service turnaround duration was operationalized through an embedded Random Forest Regressor trained and evaluated exclusively on 10,000 simulated operational orders (Dataset B) using Scikit-learn (version 1.8.0), Pandas (version 3.0.1), and NumPy (version 2.4.3). The finalized model artifact consists of 300 decorrelated decision trees constrained to a maximum depth of 12, taking Feature Set C (12 operational predictors known at intake: total_pairs, basic_cleaning_qty, full_reglue_qty, minor_reglue_qty, unyellowing_qty, minor_restoration_qty, color_renewal_qty, rush_indicator, distinct_service_types, total_service_applications, intake_day_of_week, and intake_month) as input and outputting continuous predicted turnaround days. The model binary (completion_model.pkl, cryptographic digest SHA-256: 9ce390ca5f0197fe0eef86086ccfd78b79b18b37c19eae76fca7d518bbfeac3b) is loaded directly into server memory upon startup to provide operational inferences without third-party external API latency.
Section 3.9.3 Relational Database Layer and Environment Separation
#### 3.9.3 Relational Database Layer and Environment Separation Data persistence strictly enforces environment separation between cloud production, local development, and automated testing: 1. Production Database: In cloud production, the system utilizes Heroku Postgres on the Essential-0 tier executing PostgreSQL (compiled version 17.10 on 64-bit aarch64 architecture). Database communication is mediated by SQLAlchemy (version 2.0.48) utilizing the Psycopg 3 driver (psycopg, version 3.3.4). Transport encryption is enforced through mandatory TLS (sslmode=require, sslnegotiation=direct). Because cloud dynos are stateless and subject to periodic cycling, SQLAlchemy was configured with NullPool, establishing direct connections per transaction and preventing connection pool starvation across dyno sleep/wake cycles. The system implements a strict fail-closed policy (Guard P0-5): if PostgreSQL connectivity is interrupted in production, the application returns HTTP 503 Service Unavailable, strictly prohibiting silent fallback to SQLite in production to prevent data divergence. 2. Local Development and Offline Continuity: For local workstation development, the system utilizes SQLite (version 3.50.4 C-library) with Write-Ahead Logging (WAL) enabled (shoelotskey.db). A development guard (Guard P0-2) automatically blocks localhost instances from connecting to the remote production database without explicit administrative override (ALLOW_REMOTE_DB=true), protecting live operational records. 3. Automated Testing Sandbox: Automated regression test suites are executed against an isolated SQLite test database (qa_sandbox.db) via Pytest, ensuring zero interference with development or production data.
Section 3.9.4 Security, Authentication, and Session Controls
#### 3.9.4 Security, Authentication, and Session Controls User authentication enforces a hybrid stateful architecture combining signed JSON Web Tokens (JWT) with database session tracking. Tokens are cryptographically signed via HMAC-SHA256 (HS256) utilizing PyJWT (version 2.12.1) with a dynamically injected secret key (JWT_SECRET) and an 8-hour expiration period (480 minutes). Token payloads contain a session identifier (sid) that is validated against active records in the user_sessions database table, enabling immediate revocation upon logout or administrative override. User passwords are cryptographically hashed, rather than encrypted, using Bcrypt (version 5.0.0 via passlib version 1.7.4) utilizing a standard work factor of 12 with per-user salt generation. To mitigate automated brute-force attacks on authentication endpoints, the system enforces progressive account lockout: three consecutive failed login attempts trigger an automatic 15-minute account lock. The primary administrator account is immune to automated lockout to prevent denial-of-service against system management. Secondary authorization for supervisor overrides on discounts and refunds enforces an identical 3-attempt, 15-minute lockout rule. These specific security controls were verified through automated regression suites (test_granular_permissions.py and test_cyberattack_defense.py).
Section 3.9.5 Production Deployment and Evaluation Provenance
#### 3.9.5 Production Deployment and Evaluation Provenance The production application was hosted on Heroku under the custom domain https://shoelotskey-villamor-pasay.app, with DNS managed through Name.com and TLS 1.3 certificates provisioned via Heroku Automated Certificate Management (ACM). The system configuration was evaluated across two documented empirical milestones: (1) a formal pilot implementation conducted from September 2 to 16, 2026, during which 31 digital job orders were processed under live counter operations; and (2) an evaluator testing period conducted from September 17 to 22, 2026, comprising IT Expert ISO/IEC 25010 evaluations and staff Technology Acceptance Model (TAM) questionnaires. Deployment release records indicate that prior to evaluator testing, the production slug was remediated by removing heavy deep-learning dependencies (EasyOCR/PyTorch) to operate within Heroku's slug size boundaries, retaining the Google Gemini Vision API for document digitization. Forensic inspection of live Heroku releases confirms the evaluation manuscript baseline corresponds to Release v150 (Git commit 1f93846c), while current production execution corresponds to Release v152 (Git commit 777f8efb). Database telemetry confirms 15.8 MB storage utilization across 38 relational tables with continuous WAL protection active.
