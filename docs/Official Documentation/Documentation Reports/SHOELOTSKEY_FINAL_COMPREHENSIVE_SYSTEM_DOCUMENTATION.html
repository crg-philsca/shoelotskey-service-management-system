5. System Architecture (3-Tier) Implemented

The system utilizes a strict 3-tier modular architecture, confirmed in the repository structure:

  • Presentation Layer (Frontend): React 18, TypeScript, Vite. A Single Page Application (SPA) providing responsive interfaces. Component routing is handled entirely client-side via react-router-dom. UI components leverage standard CSS without reliance on external CDNs.
  • Application Layer (Backend API): Python 3.12, FastAPI. Exposes RESTful endpoints, handles Pydantic validation, enforces JWT RBAC, and houses the scikit-learn machine learning engine. It runs on a Gunicorn server utilizing Uvicorn asynchronous workers.
  • Data Layer (Database): PostgreSQL 16. A relational database normalized to 3NF, interfaced via SQLAlchemy 2.0 ORM to prevent SQL injection.
Architecture Fact Check: The system is a modular monolith. It does not use microservices. It does not have high-availability clustering. It uses a single Heroku web dyno connecting to a single Heroku Postgres instance.

6. Database Design (3NF) Verified

The PostgreSQL database schema was audited and verified to conform strictly to Third Normal Form (3NF):

  • 1NF (Atomic Values): No comma-separated strings or arrays. Multi-pair orders are extracted to order_shoes and order_services junction tables.
  • 2NF (No Partial Dependencies): Every table utilizes a single-column surrogate primary key (id). Junction tables (e.g., order_service_addons) depend entirely on their composite keys.
  • 3NF (No Transitive Dependencies): Customer data (name, phone) is isolated in customers. The job_orders table only stores the foreign key customer_id. Service prices are isolated in services.

Transactional Integrity: SQLAlchemy session blocks ensure atomic operations. For example, when an order transitions to for-release, the order status update and the associated inventory deductions occur within the same ACID transaction. If inventory deduction fails due to insufficient stock, the entire order status rolls back.

7. End-to-End Traces Verified

The following traces definitively prove the flow of data across the 3 tiers.

Trace 1: Job Order Creation

1. React UI: Staff completes JobOrderForm.tsx.

2. Frontend Request: fetch('/api/orders', { method: 'POST', headers: {'Authorization': 'Bearer ...'} })

3. FastAPI Routing: router.post("/orders") intercepts the request.

4. Validation & Auth: Depends(get_current_user) validates JWT. Pydantic JobOrderCreate schema validates JSON payload types.

5. Business Logic: main.py calculates deterministic release date. (Optionally calls ml_engine.predict for advisory date).

6. SQLAlchemy ORM: Creates JobOrder instance, maps order_shoes and services.

7. PostgreSQL: Executes parameterized INSERT INTO job_orders ... RETURNING id.

8. Response: FastAPI returns HTTP 201 Created with the new Job Order ID.

Trace 2: Unauthorized Analytics Access

1. Direct Access: Staff manually types /analytics in the URL bar.

2. React UI: Fetches /api/reports/sales.

3. FastAPI Auth: @router.get("/reports/sales", dependencies=[Depends(require_role("OWNER"))]) executes.

4. Token Decode: PyJWT decodes the token and inspects the role claim.

5. Rejection: Role is STAFF, not OWNER. FastAPI raises HTTPException(status_code=403, detail="Not enough permissions").

6. React UI: Catches 403 error, redirects staff to /dashboard with an error toast.

8. Deployment Architecture Implemented

The system is deployed entirely on Heroku Platform-as-a-Service.

  • Web Dyno: Runs the Python backend using Gunicorn with Uvicorn async workers (web: gunicorn -w 1 -k uvicorn.workers.UvicornWorker main:app). The React frontend is compiled into static assets via Vite (npm run build) and served statically by the FastAPI server using StaticFiles.
  • Database: Heroku Postgres Essential-0 tier. Configured via DATABASE_URL environment variable.
  • Domain: https://shoelotskey-villamor-pasay.app (managed via Name.com) with Automated Certificate Management (ACM) for HTTPS.
  • Offline Incapability: The architecture strictly requires an internet connection. There is no IndexedDB local queuing or Service Worker caching for offline job order creation.

13. Machine Learning Model Implemented

Model Choice: RandomForestRegressor (scikit-learn). Chosen over neural networks or linear regression for its robustness against non-linear interactions (e.g., drying time for cleaning + reglue doesn't scale linearly) and resistance to overfitting on small datasets.

Target Variable: CompletionDays (Calculated mathematically as Claimed Date - Date Received).

14. ML Metrics & Advisory Rule Verified

The ML model was trained on a highly constrained historical dataset of 35 human-validated eligible records (28 train, 7 test). The metrics achieved are:

  • MAE (Mean Absolute Error): 7.61 days
  • RMSE: 8.93 days
  • R² Score: 0.1959
Critical Architectural Limitation (The Advisory Rule):
An R² of 0.1959 mathematically proves high variance. Furthermore, the "Claimed Date" target variable includes the customer's delay in picking up the shoes, adding human noise unrelated to actual repair time.

Therefore, the system enforces a Dual-Tier Date Architecture:
1. Authoritative Business Rules: Deterministic calculation (e.g., Service A = 3 days, Rush = -1 day) yields the Official Release Date provided to the customer.
2. Advisory ML Prediction: Yields an Advisory Date visible only to staff as historical context (e.g., "historically, similar orders took 5 days longer to actually be claimed").

16. Authentication (JWT/Bcrypt) Verified

All authentication is handled server-side. Passwords are never stored in plain text.

  • Hashing: The backend/auth_utils.py file utilizes bcrypt with a salt round of 12. Validated via the bcrypt.checkpw() function.
  • Tokens: Upon successful login, FastAPI generates a JSON Web Token (JWT) signed using the HMAC-SHA256 algorithm and a server-side secret key (SECRET_KEY in `.env`).
  • Transmission: Tokens are returned to the React frontend and sent in the Authorization: Bearer header for all subsequent API requests.
  • Expiration: JWTs enforce an absolute expiration of 24 hours. A separate frontend mechanism in App.tsx clears the token from localStorage after 30 minutes of inactivity.

17. OWASP Top 10 Mitigation Verified

The system architecture addresses the following OWASP Top 10 vulnerabilities:

  • A01 Broken Access Control: Enforced via FastAPI Depends(). The require_role dependency actively intercepts requests and issues HTTP 403 before endpoint execution.
  • A02 Cryptographic Failures: Addressed via Bcrypt hashing and Heroku HTTPS (Automated Certificate Management).
  • A03 Injection: 100% mitigated. SQLAlchemy 2.0 ORM parameterizes all variables. There is zero raw SQL string concatenation (e.g., f"SELECT * FROM users WHERE username='{user}'" is absent).
  • A04 Insecure Design: Brute-force protection implemented. 3 consecutive failed logins trigger a 15-minute account lockout, mitigating automated credential stuffing.
  • A07 Identification & Auth Failures: Weak passwords rejected at registration. 30-minute frontend inactivity timeout automatically clears session tokens.
