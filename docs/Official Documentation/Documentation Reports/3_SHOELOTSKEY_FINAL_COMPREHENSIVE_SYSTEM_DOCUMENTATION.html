01. Executive Summary

Verified

Project Identity: A Web-Based Service Management System with Data Analytics Using Machine Learning Algorithms for Shoelotskey Villamor-Pasay.

Business Context & Problem: Shoelotskey Villamor-Pasay faced operational inefficiencies in manual job order tracking, manual status updates, inventory desynchronization, and subjective estimations of service completion dates. The lack of a centralized system hindered scalability and accurate reporting.

Major System Functions: The deployed system provides centralized job order management, service catalog control, inventory tracking, and automated sales reporting.

ML Purpose: An advisory Machine Learning model (Random Forest Regressor) supplements authoritative business rules by predicting service completion dates based on historical order-to-claim data, providing data-driven turnaround time estimates.

Evaluation Approach: System software quality was formally evaluated against 9 characteristics of ISO/IEC 25010:2023 using a 45-statement instrument. User acceptance is measured via the Technology Acceptance Model (TAM) containing 4 constructs and 20 statements.

Major Limitations: The ML model relies on a small historical dataset (35 eligible records) yielding modest predictive metrics (R²=0.1959). Consequently, ML serves as an advisory tool, while official release dates remain strictly governed by business rules. The system relies entirely on internet connectivity and PostgreSQL availability.

02. Project Overview

Implemented

The system is specifically engineered for the operational workflows of Shoelotskey Villamor-Pasay. It targets the core business flow: receiving footwear, assessing condition, establishing required services (cleaning, reglue, restoration), providing quotes, and tracking progress through to final claim.

Intended Users:

  • Owner: Full system access, financial reporting, employee management, service configuration.
  • Staff/Technicians: Job order creation, status updating, basic inventory deduction.

03. Project Objectives

Verified

The project adheres to five strictly documented objectives:

  • Objective 1: To develop a centralized digital job order management system for tracking shoe restoration services.
  • Objective 2: To integrate a machine learning algorithm (Random Forest Regressor) for predicting service completion dates.
  • Objective 3: To implement analytics and reporting modules for sales, services, and inventory tracking.
  • Objective 4: To evaluate the software quality of the system using the ISO/IEC 25010:2023 framework.
  • Objective 5: To evaluate user acceptance using the Technology Acceptance Model (TAM).
Traceability Note: All system features, evaluations, and manuscript findings trace directly back to these five approved objectives. Unrelated or unverified goals (such as 100% accuracy guarantees) are not part of the project objectives.

04. Scope and Limitations

Verified

Included Scope: Job order creation, role-based access control (Owner/Staff), inventory deduction upon service completion, payment tracking, basic analytics dashboard, and advisory ML completion predictions.

System Limitations:

  • No Offline Capability: The system requires an active internet connection. There is no local caching or offline queueing implemented.
  • ML Dataset Constraints: The ML model is constrained by a small validated historical dataset (35 records), limiting its predictive power.
  • No Customer Portal: Customers cannot log in to track orders themselves; status tracking relies on SMS/external communication or direct inquiry.
  • No Automatic Retraining: The Random Forest model must be manually retrained by an administrator when new historical data is validated; it does not retrain automatically on the fly.
  • Single Branch: The architecture and database are designed for a single branch (Villamor-Pasay) and do not support multi-tenant or multi-branch franchising out of the box.

05. System Overview

Implemented

The Shoelotskey Service Management System operates on a classic 3-tier web architecture:

  • Presentation Layer: A React.js Single Page Application (SPA) providing responsive UI for Staff and Owners.
  • Application Layer: A Python FastAPI backend handling business logic, authentication, and serving the scikit-learn ML model.
  • Data Layer: A PostgreSQL relational database managing 3NF-normalized state, connected via SQLAlchemy ORM.

Data flows from the browser via REST API (JSON) over HTTPS to the FastAPI backend. The backend validates tokens, enforces RBAC, interacts with PostgreSQL, and invokes the ML engine synchronously during job order estimation.

08. Application Architecture

Verified

The application architecture enforces strict separation of concerns:

  • Routers (routers/): Define API endpoints (e.g., /auth, /orders). They handle HTTP requests, responses, and dependency injection (DB sessions, current user).
  • Schemas (schemas.py): Pydantic models define strict input/output data shapes, ensuring invalid data is rejected before hitting business logic.
  • Models (models.py): SQLAlchemy classes map to PostgreSQL tables, defining relationships and constraints.
  • ML Engine (ml_engine.py): Encapsulates model loading, feature extraction, and inference. The application layer calls this service without needing to know scikit-learn internals.

09. Frontend Architecture

Implemented

The React frontend is built as a modular Single Page Application:

  • Routing: react-router-dom handles navigation between 20+ views (Dashboard, Job Orders, Inventory, etc.) without page reloads.
  • Components: Reusable UI elements (modals, tables, buttons) exist in src/app/components/.
  • State Management: Context API (e.g., OrderProvider, InventoryProvider) manages global state, while local component state uses useState.
  • API Integration: Standard fetch API calls are centralized or handled within contexts, attaching the JWT Bearer token to authenticated requests.
  • Protection: A ProtectedRoute wrapper component enforces role-based rendering (Owner vs Staff).

10. Backend Architecture

Implemented

The FastAPI backend utilizes dependency injection for database sessions and authentication. Every protected endpoint injects get_current_user or require_role to verify JWT validity and permissions. Business logic (e.g., inventory deduction upon job order completion) is handled within transaction blocks to ensure atomicity—if deduction fails, the order status update rolls back.

11. Database Architecture

Verified

Production: The system strictly utilizes PostgreSQL on Heroku. PostgreSQL provides robust concurrency control, JSONB support (if needed), and automated Heroku backups.

Local Development: A local SQLite fallback (shoelotskey.db) is configured purely for offline development and local disaster recovery testing.

Production Guard: The database.py configuration explicitly prevents silent fallback to SQLite in production. If the Heroku DATABASE_URL is unreachable, the system will fail safely (503 Service Unavailable) rather than serving an isolated, empty local SQLite file.

12. Database Design and Data Model

Implemented

The schema adheres to Third Normal Form (3NF) to eliminate data redundancy and anomalies.

  • Core Entities: users, customers, orders, items, services, inventory.
  • Lookup Tables: roles, status, service_categories, conditions, payment_methods.
  • Mapping Tables: item_service_mapping, item_condition_mapping to resolve many-to-many relationships.
  • Historical/ML Data: historical_orders, historical_predictions to isolate training data from live transactional data.

Foreign keys enforce referential integrity (e.g., an order cannot belong to a non-existent customer; an item cannot reference a deleted service without cascading or nullifying appropriately based on audit requirements).

13. Database Administration

Verified

Database administration is managed through Heroku Postgres dashboards and SQLAlchemy. Migrations are handled via initialization scripts (setup.sql) during deployment. Audit logs are maintained in audit_logs and status_log tables to track critical business events (who changed an order status, when, and from what to what).

15. Job Order Management Workflow

Implemented

The core business workflow:

  1. Creation: Staff inputs customer details, selects shoe items, conditions, and required services.
  2. Estimation: System calculates the Official Release Date via Business Rules, and provides an advisory ML Prediction.
  3. Payment: Downpayment or full payment is recorded.
  4. Processing: Status moves from new-order to on-going.
  5. Completion: Status moves to for-release. Inventory is automatically deducted based on services performed.
  6. Claiming: Status moves to claimed. The total duration (Claimed Date - Date Received) becomes eligible for future ML training if validated.

16. Service Management

Implemented

Owners manage the service catalog. Each service includes a base price and a baseline duration_days. The official Business Rules engine uses these duration values, along with combination logic (e.g., performing a Full Reglue + Restoration overrides standard additive timelines), to compute the official customer commitment date.

17. Inventory Management

Implemented

Tracks physical consumables (glues, cleaners, paints). Items have current quantities and low-stock thresholds. When a job order is marked for-release, the system triggers business logic to deduct relevant inventory items associated with the performed services. Transactions are logged in inventory_logs for auditability.

Limitation: Concurrent inventory deductions rely on standard PostgreSQL transactions. Extremely high concurrency could cause lock contention, though this is negligible at current operational volumes.

18. Sales and Expense Management

Implemented

Records all incoming revenue (payments against job orders or direct POS sales) and outgoing shop expenses. Calculates gross and net totals over selected periods. Permissions ensure only Owners can modify historical financial records.

19. Analytics and Reporting

Implemented

Aggregates data for the Dashboard. Provides visualizations for monthly revenue, popular services, and pending job order distribution. Allows exporting data for external accounting. Filtering is supported by date ranges and status.

20. User Management and RBAC

Implemented

Enforces strict separation of duties:

  • Owner: Can access Analytics, Financials, User Management, Service Configuration, and Historical Data validation.
  • Staff: Restricted to Job Orders, basic Inventory views, and daily operational tasks. Backend routes explicitly reject requests from Staff tokens attempting to access Owner endpoints.

21. Business Rules

Verified
Crucial Distinction: The Official Release Date is calculated by a deterministic Business Rules engine based on the service catalog (e.g., Service A takes 3 days, Service B takes 2 days). This provides the legally committed date to the customer.

The ML model acts strictly as an advisory overlay to indicate if historical trends suggest the order will take longer or shorter than the official rule.

22. Machine Learning System

Implemented

The system integrates a RandomForestRegressor trained via scikit-learn. It predicts CompletionDays (the number of days from order receipt to claim). The trained model is serialized as completion_model.pkl and loaded into memory by the FastAPI backend on startup.

23. ML Dataset and Features

Verified

The canonical deployed feature vector strictly contains 18 features extracted from the job order:

total_pairs, basic_cleaning_qty, full_reglue_qty, minor_reglue_qty, full_restoration_qty, minor_restoration_qty, color_renewal_qty, unyellowing_qty, priority_encoded, grand_total, day_of_week_received, month_received, scratches_count, yellowing_count, sole_separation_count, deep_stains_count, rips_holes_count, worn_out_count.

The model does not currently use real-time technician workload, queue volume, or weather latency, as these features are not present in the historical dataset.

24. ML Training and Evaluation

Verified

Parameters: n_estimators=150, max_depth=10, random_state=42.

Target Variable: CompletionDays = ClaimedDate - DateReceived (filtered to valid ranges of 1-60 days).

Documented Dataset & Metrics:

  • Eligible Records: 35
  • Training Split: 28 records
  • Testing Split: 7 records
  • MAE (Mean Absolute Error): 7.61 days
  • RMSE: 8.93 days
  • R² Score: 0.1959
Honest Reporting: The R² score of 0.1959 indicates modest predictive power, largely due to the extremely small dataset size (35 records). The system does not claim 85% or 92% accuracy. This mathematical reality is why the ML is explicitly classified as an advisory feature, not a replacement for business rules.

25. ML Limitations and Interpretation

Verified

The primary limitation is data volume. Machine learning requires hundreds to thousands of records to identify robust patterns. With only 35 eligible records, the model is highly susceptible to variance. Furthermore, the target variable (Order to Claim) includes the customer's delay in picking up the shoes, introducing noise unrelated to the actual repair time. Future enhancements require separating "Repair Completed Date" from "Claimed Date" in the data model.

26. OCR and Historical Data

Partially Implemented

Historical paper records are processed via OCR to build the ML dataset. The preferred production workflow involves scanning physical tickets, preprocessing, and structured extraction (e.g., using Gemini Vision or local fallbacks like Tesseract). Heavy local OCR models (like EasyOCR or TrOCR) are strictly excluded from the Heroku production deployment due to slug size limitations (500MB max) and memory constraints.

27. Data Validation and Human Review

Implemented

Crucial Rule: OCR output is never automatically trusted. Extracted data enters a PENDING REVIEW state. A human administrator must structurally validate dates, quantities, and services. Only after explicit human correction and approval does a record become VALIDATED and eligible for ML training.

28. Authentication and Authorization

Implemented

Authentication utilizes stateless JSON Web Tokens (JWT). Passwords are securely hashed using bcrypt with salting. The FastAPI backend employs dependency injection (oauth2_scheme) to extract and validate tokens on every protected route. Authorization is enforced by checking the role claim embedded in the JWT payload against endpoint requirements.

29. Security Architecture

Implemented

Security is implemented in depth:

  • Network: HTTPS enforcement via Heroku ACM.
  • Application: Input validation via Pydantic schemas prevents malformed payloads. SQLAlchemy ORM inherently parameterizes queries, preventing SQL Injection.
  • Session: A 30-minute inactivity timeout is implemented in the React frontend (App.tsx), automatically clearing tokens and terminating sessions.
  • Secrets: JWT secret keys and database URLs are managed via Heroku Config Vars, never hardcoded in source.

30. OWASP Security Review

Verified

Review against OWASP Top 10:

  • A01: Broken Access Control: Mitigated via strict backend route protection and RBAC.
  • A02: Cryptographic Failures: Mitigated via bcrypt hashing and HTTPS transit.
  • A03: Injection: Mitigated via SQLAlchemy ORM parameterization.
  • A07: Identification and Authentication Failures: Mitigated via strong JWT validation and 30-minute inactivity timeouts.

Remaining Risk: Lack of multi-factor authentication (MFA) and aggressive rate limiting on login endpoints.

32. Error Handling

Implemented

The backend sanitizes error responses. Database connection failures or internal exceptions return generic 500 Internal Server Error messages to the client, preventing stack trace or infrastructure disclosure. Pydantic validation errors return structured 422 Unprocessable Entity responses detailing exactly which field failed.

33. Reliability and Failures

Verified

If the ML service fails (e.g., model file corrupted), the API gracefully falls back to heuristic business rules, appending a "fallback_reason" to the response. If the database is unreachable, the system fails safely, returning 503 errors rather than attempting unauthorized local caching. Invalid JWTs immediately return 401 Unauthorized, triggering frontend redirection to login.

34. Data Synchronization

Verified

As a purely web-based application, data synchronization is synchronous. Clients read and write directly to the central PostgreSQL database via the API. There is no complex multi-master synchronization or edge caching implemented.

35. Internet Interruption / Offline

Verified

The system is not offline-capable. If internet connectivity is lost, frontend API calls will fail, and the UI will display generic network error messages. State changes cannot be queued locally for later synchronization. The business must rely on manual paper ticketing during internet outages, transcribing them into the system once connectivity is restored.

36. Backup and Recovery

Implemented

Heroku Postgres provides automated daily backups and continuous protection (WAL archiving). In the event of catastrophic data corruption, administrators can restore the database to a specific point in time using Heroku CLI tools. Local SQLite backups are not used for production data recovery.

37. Maintainability and Code Quality

59. Defense Q&A Bank

Why Random Forest? Why not Linear Regression or Deep Learning? ▼

Random Forest Regressor was chosen because it handles non-linear relationships well, is robust to outliers, and requires less data scaling than neural networks. Deep learning requires thousands of records, which we do not have. Linear Regression assumes linear relationships, which shoe repair timelines rarely follow (e.g., adding a service doesn't scale time linearly; it involves parallel drying times).

Why is the ML R² score only 0.1959, and MAE 7.61? ▼

Machine learning requires volume. We only have 35 eligible, human-validated historical records. With n=35, the model struggles to generalize, leading to high variance (MAE 7.61 days). Furthermore, our target variable is "Claimed Date" minus "Date Received". Customers often delay picking up their shoes days after the repair is finished, injecting random noise into the data. This mathematically proves why our ML is strictly an advisory feature, while Business Rules dictate the official release date.

What is the difference between Official Release Date and ML Prediction? ▼

The Official Release Date is deterministic—it is calculated by our Business Rules engine based on the defined service catalog (e.g., cleaning takes 3 days). This is the legally committed date given to the customer. The ML Prediction is advisory—it looks at historical trends to warn the staff "historically, similar orders took 5 days longer to actually be claimed."

Why use ISO/IEC 25010 instead of 9126? Why 9 characteristics? ▼

ISO/IEC 25010:2023 is the modern, current international standard for software quality, replacing the obsolete 9126. It specifically addresses modern concerns like Security and Compatibility, which are critical for a web-based, cloud-hosted system.

How is security and RBAC enforced? Can Staff access Owner functions? ▼

Security is enforced via stateless JWT (JSON Web Tokens). When a user logs in, the backend cryptographically signs a token containing their role. Every API request must include this token. The FastAPI backend extracts the role and explicitly rejects (403 Forbidden) any Staff token attempting to hit an Owner-only route (like Sales Analytics or User Management). Modifying the frontend UI cannot bypass this backend protection.

What happens when the internet goes down? ▼

The system is a cloud-hosted web application and requires an active internet connection to communicate with the Heroku servers. If the internet goes down, the system cannot be used. The shop must revert to manual paper ticketing and encode the data later. We do not claim offline capabilities.
