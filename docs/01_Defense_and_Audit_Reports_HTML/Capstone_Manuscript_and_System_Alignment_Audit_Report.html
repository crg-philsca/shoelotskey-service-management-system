3. The 8 Critical Manuscript Revisions (Word-for-Word Replacements)

To eliminate any vulnerability during the oral defense, apply these exact 8 text replacements to the capstone manuscript:

🔴 Revision 1: ISO/IEC 25010:2023 Nine-Characteristic Standard

The Problem: Chapter 1 (Pages 4–5, RQ4; Page 10, Objective 4) and Chapter 4 list the old 2011 standard (7 characteristics including Portability).
The Reality: The approved, signed evaluation instrument uses the current ISO/IEC 25010:2023 edition containing 9 product-quality characteristics.

Exact Replacement Text for Chapter 1 (RQ4 and Objective 4) & Chapter 4:
"4. Evaluate the software product quality of the developed system based on the ISO/IEC 25010:2023 international standard across nine (9) characteristics: Functional Suitability, Performance Efficiency, Compatibility, Interaction Capability, Reliability, Security, Maintainability, Flexibility, and Safety."

🔴 Revision 2: Likert Scale Correction (4-Point Forced-Choice)

The Problem: Chapter 4 (Page 88) erroneously states: "using a 5-point Likert scale questionnaire based on ISO/IEC 25010 and Technology Acceptance Model (TAM) criteria."
The Reality: Both instruments explicitly employ a 4-point rating scale ($4 = \text{Highly Acceptable}, 3 = \text{Acceptable}, 2 = \text{Less Acceptable}, 1 = \text{Not Acceptable}$).

Exact Replacement Text for Chapter 4 (Methodology & Instrument Section):
"The evaluation questionnaires utilized a four-point forced-choice Likert scale (4 – Highly Acceptable, 3 – Acceptable, 2 – Less Acceptable, and 1 – Not Acceptable). A four-point format was specifically implemented to eliminate neutral response bias ('undecided') and obtain definitive, actionable evaluative feedback from both external IT practitioners and operational enterprise users."

🔴 Revision 3: Machine Learning Feature Contract (Actual 18 Features vs Fabricated Claims)

The Problem: Chapters 1, 2, and 3 claim the Random Forest model takes "technician queue length, assigned staff, shoe material type, condition severity, and previous turnaround times" as input features.
The Reality: The system does not assign technicians or track drying times. The production model (`historical_ml_engine.py`) takes exactly 18 concrete operational features captured at intake.

Exact Replacement Text for Chapter 3 (Machine Learning Methodology):
"The Random Forest Regressor utilizes eighteen (18) structured operational features extracted directly during job order creation: total shoe pairs (`total_pairs`), individual service quantities (`basic_cleaning_qty`, `full_reglue_qty`, `minor_reglue_qty`, `full_restoration_qty`, `minor_restoration_qty`, `color_renewal_qty`, `unyellowing_qty`), encoded priority (`priority_encoded`: Regular, Rush, Premium), transaction amount (`grand_total`), calendar intake factors (`day_of_week_received`, `month_received`), and binary defect indicators (`scratches_count`, `yellowing_count`, `sole_separation_count`, `deep_stains_count`, `rips_holes_count`, `worn_out_count`). The model predicts a continuous turnaround duration in days."

🔴 Revision 4: 85% ML Target Benchmark vs Regression Metrics ($MAE$, $RMSE$, $R^2$)

The Problem: Objective 2 sets an "accuracy of 85% or higher compared to manual estimation," and the text asserts that the model produces "accurate pick-up dates."
The Reality: Regression algorithms output continuous values; claiming an "85% accuracy percentage" is mathematically invalid.

Defensive Wording for Chapter 4 (Results and Discussion):
"While an 85% accuracy threshold was formulated as the initial exploratory target in the capstone proposal, continuous duration prediction is properly evaluated using regression metrics: Mean Absolute Error (MAE) and Root Mean Squared Error (RMSE). On the validated historical micro-enterprise dataset, the Random Forest model achieved an MAE of approximately 7.61 days. Consequently, the machine learning component is maintained as an Advisory Forecast rather than an authoritative release date mechanism, ensuring shop operations remain dependable."

Exact Replacement Text for Chapter 3 & Chapter 4:
"The system enforces a dual-tier turnaround estimation architecture: (1) Authoritative Business Rules calculate the committed customer release date based on standard base service durations, add-on days, and rush reductions; and (2) an Advisory Random Forest Regressor calculates an empirical forecast for staff planning. The advisory prediction cannot alter, postpone, or overwrite the official customer commitment date."

🔴 Revision 6: Administrative ML Retraining vs Continuous Online Learning

The Problem: Chapter 1 claims: "The system automatically learns from its mistakes... if an ML prediction was wrong, the actual completion time is fed back in real-time."
The Reality: Random Forest requires batch retraining. In the system, retraining is an Owner-only administrative operation (`/api/historical/train`).

Exact Replacement Text for Chapter 1 (Conceptual Framework):
"The system incorporates a closed-loop historical data ingestion pipeline. Completed and validated job orders are archived in the historical dataset. The shop owner can periodically execute an administrative retraining command to update the Random Forest model using verified operational records, ensuring the model adapts to long-term shop trends over time."

🔴 Revision 7: Respondent Sample Typographical Errors and Evaluation Dates

The Problem: Chapter 4 contains glaring typographical errors: "one (1) business owner and five (4) staff members" and "same six (5) participants." It also dates testing to June 2025.
The Reality: The TAM evaluation sample is Owner + 2 Staff members. The formal evaluation questionnaires are dated July 27, 2026, and IT Expert reviews were conducted in September 2026.

Exact Replacement Text for Chapter 4 (Sample and Timeline):
"The research distinguished between the preliminary requirements analysis phase conducted in 2025 and the formal system evaluation conducted in July–September 2026. The operational usability evaluation (TAM) was administered to three (3) primary enterprise stakeholders: the business owner and two (2) designated front-desk staff. Software product quality (ISO/IEC 25010:2023) was evaluated independently by three (3) qualified external IT practitioners."

🔴 Revision 8: Cloud Infrastructure & Security Clarifications

The Problem: Chapter 3 claims a "Node.js real-time file monitoring daemon" and claims Heroku Postgres provides "high availability with instant failover."
The Reality: The backend is Python FastAPI; there is no Node.js security agent. The database is Heroku Postgres Essential-0, which does not provide HA replicas.

Exact Replacement Text for Chapter 3 (Deployment Architecture):
"The production environment is hosted on Heroku dynos connected to a managed Heroku PostgreSQL relational database instance utilizing SSL-encrypted connections (`sslmode=require`) and automated daily backups. Application security is enforced directly within the FastAPI backend via JSON Web Token (JWT) authentication, bcrypt password hashing, parameterized SQL queries via SQLAlchemy ORM, and defensive input validation."

5. Defensive Guardrails: What NOT to Do

⚠
Strict Guidelines to Protect System Integrity Prior to oral defense and production redeployment, adhere strictly to these boundaries:
  • ✕ Do NOT alter the frozen 45 ISO survey statements or 20 TAM items: The surveys have been signed and administered. Modifying statements now invalidates the empirical data.
  • ✕ Do NOT implement technician assignment or staff queues: The shop does not assign individual technicians to jobs, and the ML model does not track staff capacity. Introducing this would create unbacked claims.
  • ✕ Do NOT claim 85% ML accuracy without regression context: Frame 85% as the initial proposal benchmark and report continuous regression metrics honestly ($MAE \approx 7.6\text{ days}$).
  • ✕ Do NOT attempt heavy database schema migrations: The PostgreSQL cloud schema is stable and tested. Destructive migrations prior to defense create catastrophic downtime risks.
  • ✕ Do NOT add unvetted third-party SMS or OCR daemons to Heroku: Free or third-party SMS APIs (Twilio/Semaphore) require live credit balances and webhook secrets that can fail during live defense demonstrations.
