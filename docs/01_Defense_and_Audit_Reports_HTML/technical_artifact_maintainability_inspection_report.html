1. Scope and Methodology

In response to the Capstone Evaluation Panel's directive, this inspection provides an empirical, artifact-based evaluation of system maintainability under ISO/IEC 25010. Academic software quality evaluations frequently rely solely on questionnaire-based expert ratings (e.g., Likert scales), which capture subjective perception rather than technical source-level properties. To provide rigorous defense-ready evidence, this technical audit directly inspects the source-code artifacts, database schemas, dependency configurations, test suites, and documentation residing in the official repository.

Inspection Protocol Rules

  • Strict Zero Fabrication: Every metric, line count, table mapping, dependency, and finding is verified directly against repository files.
  • Non-Destructive Read-Only Operation: No source code was altered, deleted, or refactored during the inspection.
  • Objective Flaw Reporting: Weaknesses, architectural anti-patterns, duplicated logic, dead dependencies, and large files are reported transparently.
  • Explicit Boundary Documentation: The production PostgreSQL database is a live remote cloud instance; local inspection is strictly limited to the authoritative SQLAlchemy ORM definitions (backend/models.py), database connection handlers (backend/db/database.py), and the local development SQLite database (backend/db/shoelotskey.db).

3. Detailed Artifact Inspection Findings

Artifact A: Source-Code Structure

Aspect Examined: Modularity and organization | Evidence: React/TypeScript frontend and FastAPI/Python backend
Needs Improvement

Inspected Files: backend/main.py (10,944 lines), backend/report_service.py (1,606 lines), backend/api/historical_processing.py (2,084 lines), backend/ml/ml_engine.py (583 lines), src/app/components/JobOrderForm.tsx (4,645 lines), src/app/pages/HistoricalRecords.tsx (3,972 lines), src/app/components/OrderDetailModal.tsx (3,690 lines), src/app/pages/HistoricalValidationQueue.tsx (3,506 lines).

Observed Strengths:

  • Clear top-level physical separation between the client application (src/) and backend API (backend/).
  • Specialized domains are extracted into dedicated services: reporting logic in backend/report_service.py, database session lifecycle in backend/db/database.py, and ML model training/inference in backend/ml/ml_engine.py and backend/ml/historical_ml_engine.py.
  • Reusable UI primitives in src/app/components/ui/ leverage headless Radix UI components with centralized Tailwind styling.

Identified Weaknesses & Anti-Patterns:

  • backend/main.py (10,944 lines, 522 KB) Monolithic Controller: The primary backend entrypoint contains 104 route handlers attached directly to app = FastAPI(). It intermingles routing, database session handling, status transitions, inline SQL/ORM queries, business validations, and historical ETL triggers without modular APIRouter decomposition for core entities (Orders, Inventory, Users, Expenses, Payments).
  • backend/api/historical_processing.py:22-24 Dead / Unmounted Modular Router: An entire 2,084-line module defining an APIRouter explicitly contains the comment: # NOTE: This router is NOT currently include_router()'d — live routes live in main.py. This confirms architectural drift where modularization was drafted but bypassed in favor of placing routes directly in the monolithic main.py.
  • src/app/components/JobOrderForm.tsx (4,645 lines, 325 KB) Oversized Frontend Component: This massive single component encapsulates intake form state, camera hardware capture, customer auto-completion, service pricing calculations, discount authorizations, ML lead-time estimations, and image compression in one file.
  • backend/main.py (82 function-scoped imports) Inline / Lazy Imports: Main.py contains 82 lazy imports inside functions (e.g., create_engine and sessionmaker at lines 1148, 1177, 2102, 2103) indicating circular import workarounds and tight coupling between request handlers and database engine instantiation.
Maintainability Impact: High file complexity in backend/main.py and JobOrderForm.tsx increases cognitive load during code reviews, creates risk of merge conflicts during team collaboration, and complicates isolated unit testing.

Artifact B: Source-Code Naming

Aspect Examined: Readability and analyzability | Evidence: Components, functions, classes, variables, and routes
Satisfactory with Minor Improvements

Inspected Files: backend/models.py (831 lines), backend/schemas.py (813 lines), src/app/types/index.ts (375 lines), backend/auth_utils.py (847 lines), src/app/pages/JobOrderForm.tsx.

Observed Strengths:

  • Consistent adherence to standard naming conventions: Python modules, functions, and variables follow PEP 8 (snake_case); classes use PascalCase; TypeScript files follow PascalCase for components and camelCase for functions.
  • Pydantic schemas in backend/schemas.py use clear, self-documenting suffixes (e.g., OrderCreateSchema, UserUpdateSchema, DiscountAuthorizeRequestSchema).
  • TypeScript domain interfaces in src/app/types/index.ts (e.g., JobOrder, ShoeItem, PaymentRecord, CashSession) match backend models and reflect clear domain-driven terminology.
  • RESTful API route paths are predominantly semantic and descriptive (e.g., /api/orders/{order_id}, /api/inventory/{item_id}/logs, /api/auth/login).

Identified Weaknesses & Ambiguities:

  • backend/models.py:335 & 427 Primary Key Collision (item_id): Both the Item model (table items, representing a customer repair shoe) and the Inventory model (table inventory, representing consumable warehouse stock) define their primary key column as item_id. This creates significant confusion in join queries, audit logs, and developer maintenance when distinguishing shoe line-items from raw materials.
  • backend/models.py (Mixed PK conventions) Inconsistent Primary Key Naming: Operational tables use prefixed primary keys (user_id, role_id, order_id, customer_id), whereas auxiliary tables switch to generic id (cash_sessions.id, material_consumptions.id, csv_import_batches.id, research_test_runs.id).
  • src/app/pages/JobOrderForm.tsx vs src/app/components/JobOrderForm.tsx Shadowing Component and Page Names: The page shell and the component have identical filenames, forcing an aliased import: import JobOrderFormComponent from '../components/JobOrderForm'.
  • backend/scripts/ Ambiguous Script Filenames: Maintenance scripts contain redundant and ambiguous names such as fix_db.py, fix_database_columns.py, fix_db_columns_final.py, inspect_db.py, and inspect_db_state.py.

Artifact C: Database Schema

Aspect Examined: Structural organization and modifiability | Evidence: SQLAlchemy models, SQLite local DB, schema scripts
Satisfactory with Minor Improvements

Inspected Files: backend/models.py (37 models, 831 lines), backend/db/database.py (471 lines), backend/db/shoelotskey.db (local SQLite database), docs/02_System_Architecture_and_Specifications/ENTITY_RELATIONSHIP_AND_LOGICAL_DATABASE_DESIGN.html (247 KB).

Explicit Audit Scope Boundary: As mandated by the inspection protocol, the remote Heroku PostgreSQL production cluster was NOT directly queried. This finding is derived strictly from the authoritative SQLAlchemy ORM model definitions, the active local SQLite database (shoelotskey.db), and project architectural specifications.

Observed Strengths:

  • Strong relational normalization adhering to Third Normal Form (3NF) across operational entities: separate tables for roles, permissions, user_permissions, users, customers, orders, items, services, service_categories, conditions, payments, deliveries, and expenses.
  • Proper composite primary keys and foreign keys for many-to-many bridge tables: item_service_mapping (composite PK: item_id, service_id) and item_condition_mapping (composite PK: item_id, condition_id).
  • Explicit foreign key constraints with ondelete="CASCADE" on child order elements (items.order_id, payments.order_id, status_log.order_id) preventing orphan records.
  • Forensic design in audit_logs (table audit_logs): Explicitly denormalizes username and role at event capture time with extensive code comments citing NIST SP 800-92 forensic integrity standards, ensuring audit trails remain immutable even if user records are subsequently modified or deleted.

Identified Weaknesses & Modifiability Constraints:

  • Repository Root / backend/ Absence of Alembic Database Migrations: The repository does not utilize Alembic (no alembic/ directory, no alembic.ini). Database schema evolution has been conducted through imperative, ad-hoc Python scripts in backend/scripts/ (e.g., migrate_historical_schema.py, migrate_inventory_sync_uuid.py, safe_migrate.py), creating a risk of schema drift between local SQLite and remote PostgreSQL environments.
  • backend/models.py:345 Hybrid Relational/Unstructured Storage: The items table contains a inventory_used = Column(JSON, nullable=True) column while a separate relational material_consumptions table also exists, introducing slight schema redundancy in how material deductions are recorded.
  • backend/models.py:335 & 427 Identical PK Naming: Shared item_id primary key between repair shoe line items (items) and consumable inventory items (inventory).

Artifact G: Error and Audit Logging

Aspect Examined: Analyzability | Evidence: Audit models, log_audit() calls, /api/activities endpoint, ActivityHistory.tsx
Satisfactory

Inspected Files: backend/models.py:381-420 (AuditLog model), backend/main.py:1003 (log_audit function), backend/main.py:6966 (/api/activities route), src/app/pages/ActivityHistory.tsx (2,703 lines), backend/models.py:368 (StatusLog model), backend/models.py:465 (InventoryLog model).

Observed Strengths & End-to-End Traceability:

  • Source Code -> Database -> UI Traceability: Every critical business and security event is routed through the centralized log_audit() helper in backend/main.py (called 63 distinct times across the backend).
    • 1. Source Code Invocation: Operations such as order creation, status transitions, cash session opening/closing, payments, stock changes, and user management invoke log_audit(db, action_type=..., table_name=..., record_id=..., user_id=..., username=..., role=..., old_values=..., new_values=...).
    • 2. Database Persistence: The AuditLog entity in backend/models.py writes directly to table audit_logs, recording the action type, table name, affected record ID, old/new JSON value diffs, timestamp, IP address, user agent, and a denormalized snapshot of actor username and role.
    • 3. Secure Retrieval: The endpoint @app.get("/api/activities") (backend/main.py:6966) queries audit_logs with role-based restriction (require_role(["owner", "admin"])), filtering (by module, action, username, date range), and pagination (limit/offset).
    • 4. User Interface Rendering: The Owner-only ActivityHistory.tsx page provides an administrative dashboard to inspect, filter, and audit all recorded events.
  • Specialized Domain Audit Trails:
    • Inventory Stock Movements: Recorded in table inventory_logs (InventoryLog model) tracking item_id, change_qty, reason, user_id, and created_at; exposed via /api/inventory/{item_id}/logs and rendered in InventoryDetailModal.tsx.
    • Workflow Status History: Recorded in table status_log (StatusLog model) capturing every order progression with status_id, user_id, and changed_at.
  • Forensic Integrity Compliance: Actor identities in audit_logs are denormalized snapshots rather than live foreign key joins, preserving historical integrity if a user account is deleted or modified.

Identified Minor Limitations:

  • Standard application runtime logging (Python logging) relies on console standard output/stderr rather than a structured, rotating disk file logger (e.g., RotatingFileHandler).
  • Server exceptions caught by generic except Exception as e: blocks are occasionally written into audit_logs as action_type="SERVER_ERROR", mixing runtime error traces into the business audit table.

6. Overall Maintainability Artifact-Inspection Conclusion

The objective technical inspection confirms that the Shoelotskey Service Management System exhibits a solid foundational architecture with notable strengths in relational database normalization (3NF), forensic audit logging, and backend domain testing. However, from an ISO/IEC 25010 Maintainability standpoint (specifically addressing Modularity, Analyzability, Modifiability, and Testability), the codebase contains clear, quantifiable technical debt:

  1. Modularity Deficit: Overconcentration of routing and controller logic in a single 10,944-line backend/main.py file and UI presentation in a 4,645-line JobOrderForm.tsx component. Modularizing routes via FastAPI's APIRouter and decomposing complex UI views into focused sub-components represents the single highest-impact maintainability improvement.
  2. Dependency Hygiene: Pruning 13 dead frontend dependencies, removing unused database drivers (PyMySQL), and rationalizing PostgreSQL drivers to Psycopg 3 will reduce build sizes and maintenance overhead.
  3. Database Migration Tooling: Introducing Alembic for declarative database versioning will eliminate schema drift risks between development (SQLite) and production (PostgreSQL).
  4. Test Automation Balance: Supplementing the 49 backend test scripts with automated frontend component testing (Vitest / React Testing Library) and configuring a continuous integration pipeline will provide true end-to-end regression protection.
