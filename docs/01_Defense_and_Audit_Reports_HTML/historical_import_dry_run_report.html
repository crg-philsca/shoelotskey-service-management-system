9 Date/Time Preservation Analysis (Date-Only vs. Timestamp)

Historical evidence frequently records only a calendar date (e.g. 2026-09-14) without a specific minute or hour of intake.

Prohibition of Artificial Midnight: The system must NEVER fabricate timestamps such as 12:00:00 AM or 12:00:00 PM and present them as observed business transaction times.
  • Database Representation: In SQLite/Postgres DATETIME fields, store the business date at standard ISO midnight for query compatibility (2026-09-14 00:00:00), BUT accompany it with provenance metadata: "time_precision": "DATE_ONLY" in the order's JSON metadata.
  • UI Presentation: If time_precision == "DATE_ONLY", the frontend displays 09/14/26. It only renders clock times (e.g. 09/14/26 12:31 PM) when an actual timestamp was verified.

11 Random Forest / ML Import Safety Analysis

An audit of backend/main.py (lines 4855–4935) and backend/ml/ml_engine.py revealed that invoking the standard POST /api/orders/ endpoint automatically triggers calculate_release_estimate(), which queries the Random Forest model (completion_model.pkl) and logs an ML_PREDICTION_COMPLETED audit log.

CRITICAL SAFETY FINDING: If historical orders are ingested via the standard API endpoint, the system would manufacture synthetic September 2026 predictions and backdate ML audit logs.

Mitigation Protocol:

  1. Historical batch import must execute via a dedicated batch ingestion script bypassing the interactive prediction pipeline.
  2. Imported orders must have predicted_days = None and predicted_at = None.
  3. The finalized operational Random Forest model (completion_model.pkl, v1.2) must remain 100% frozen. No automated retraining shall occur on historical records.

12 Inventory Import Safety Analysis (Zero Synthetic Consumption)

In accordance with the finalized client business rule, Shoelotskey does not use fixed automatic material consumption per service.

Inventory Status: All inventory items in backend/db/shoelotskey.db have auto_deduct = False. The historical pilot workbook documents services, but provides no evidence of exact milliliters or grams of cleaner, paint, or glue consumed per shoe.

Therefore:

  • Zero inventory movements (inventory_logs) will be created for historical orders.
  • Current stock levels in inventory will NOT be deducted or adjusted.
  • orders.inventory_applied will be set to False with inventory_used = None.

14 Provenance Strategy

Historical records must be instantly distinguishable from live system transactions:

  • PAPER_SOURCE: Primary historical evidence directly supported by paper scans (Job Orders, DSMRs, physical utility receipts).
  • IMPORTED_HISTORICAL: System records synthesized and migrated during this batch ingestion process.
  • SYSTEM_GENERATED: Real native transactions created by staff through standard UI workflows.
  • CONTROLLED_TEST: Technical verification transactions used to test RBAC, overrides, security, and ML pipelines.

In the current schema, provenance is natively preserved via historical_orders.target_provenance, historical_orders.source_type, and the JSON audit_trail column.
