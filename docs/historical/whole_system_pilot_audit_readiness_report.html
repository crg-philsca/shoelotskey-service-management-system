⏱️ Schedule & Tracking Temporal Semantics Audit

This audit investigates the precise mathematical, logical, and database mechanisms governing the six schedule timeline cards and punctuality metrics in OrderDetailModal.tsx and backend/main.py. It provides empirical verification for defense presentations and academic manuscript documentation, preventing premature inferences or semantic conflation between operational completion and customer pickup.

⚠️ Executive Summary: Three Core Semantic Clarifications
  1. Order Date Semantics: Represents the counter intake recording timestamp in orders.created_at, not physical customer arrival through the front door.
  2. Workshop Release vs. Claim Conflation: In backend/main.py (L6491 & L5748), when an order transitions to claimed without a prior independent for-release status change, the system automatically falls back to released_at = claimed_at. Identical timestamps (e.g., 07/06/26 03:45 PM) indicate this backend fallback or simultaneous counter claim, not an independent sensor of workshop completion.
  3. Turnaround Integer Operational Day Floor: An elapsed turnaround from 07:42 AM to 03:45 PM (8 hours 3 minutes) is displayed as 1 day due to calendar-day truncation and an integer operational day floor (Math.max(1, diffDays)). It does not represent 24 elapsed clock hours.

2. In-Depth Technical Tracing & Findings

1. Order Date & Intake Semantics CODE AUDITED

In backend/models.py line 242, orders.created_at is initialized to datetime.now at the moment the Job Order is persisted into the database. In OrderDetailModal.tsx lines 800-840, receivedDate prioritizes the intake ID prefix date, order.orderDate, and order.orderTime (counter intake form inputs), falling back to created_at.

Finding: The system possesses no biometric entrance cameras or door sensors. Therefore, describing created_at as "the exact moment the customer entered the store" is scientifically unverified. The correct, defensible description is: "The timestamp when the Job Order was recorded at counter intake."

2. released_at vs. claimed_at Coupling Analysis CRITICAL FINDING

Code inspection of backend/main.py reveals three specific locations where released_at is coupled to claimed_at:

# backend/main.py (Line 6490-6491 in /api/orders/{order_id}/claim) db_order.claimed_at = get_ph_now() if not db_order.released_at: db_order.released_at = db_order.claimed_at # backend/main.py (Line 5747-5748 in update_order) elif not db_order.released_at: prev_release = _first_for_release_log() db_order.released_at = prev_release.changed_at if prev_release else (db_order.claimed_at or datetime.now()) # src/app/context/OrderContext.tsx (Line 533 frontend fallback) return bo.claimed_at ? parseUTC(bo.claimed_at) : undefined;

Finding: The system permits an order to transition directly from on-going to claimed. When this occurs, released_at is automatically populated with the claimed_at timestamp. Therefore, identical timestamps (07/06/26 03:45 PM) do not independently prove immediate customer pickup; they indicate that the order was settled at the counter without a distinct, prior workshop release status logged. For research evaluation, this proxy must be explicitly documented.

3. Turnaround Calculation Math (8h 03m vs. 1 Day) MATH VERIFIED

The calculation in OrderDetailModal.tsx lines 889-899 is:

const rD = new Date(receivedDate); rD.setHours(0, 0, 0, 0); const aD = new Date(actualReleaseDate); aD.setHours(0, 0, 0, 0); const diffDays = Math.round((aD.getTime() - rD.getTime()) / (1000 * 60 * 60 * 24)); return Math.max(1, diffDays);

Step-by-step evaluation for the July 6 example:

  • Intake: 2026-07-06 07:42 AM $\rightarrow$ stripped to 2026-07-06 00:00:00.
  • Release: 2026-07-06 03:45 PM $\rightarrow$ stripped to 2026-07-06 00:00:00.
  • diffDays = Math.round(0 / 86400000) = 0 calendar days.
  • Math.max(1, 0) = 1 day.

Finding: "1 day" corresponds to Classification E (minimum display floor of 1 applied to integer calendar-day difference). It is an operational business convention ("same-day service counts as 1 operational service day"), not 24 elapsed clock hours. The actual elapsed duration is 8 hours and 3 minutes.

4. Random Forest Model Output & Post-Processing PIPELINE AUDITED

In backend/ml/ml_engine.py lines 410-421:

rf_days = float(self.model.predict([vector])[0]) # Raw float (e.g., 0.85) rf_elapsed_days = max(1, int(round(rf_days))) # Rounded to 1 integer day base_date = self._parse_base_date(order_data) # 2026-07-06 07:42:00 ml_predicted_date = base_date + timedelta(days=rf_elapsed_days) # 2026-07-07 07:42:00 final_target_date = next_open_release_date(ml_predicted_date)

Classification: MODEL OUTPUT AFTER ROUNDING + CALENDAR POST-PROCESSING.

Finding: The Random Forest regressor does not predict clock hours or produce exactly 1.0000 days. It outputs a continuous float on target Ready-for-Release Turnaround. The pipeline rounds this to the nearest integer day ($\ge 1$), and offsets the intake timestamp by timedelta(days=rf_elapsed_days) ($24.0$ hours). This preserves the intake time (07:42 AM) while ensuring store operating calendar constraints are satisfied.

5. Business Rules (10:00 PM) vs. ML (07:42 AM) SEMANTICS CLARIFIED

Both cards report a duration of "1 day", but their target timestamps diverge:

  • Business Rules (07/07/26 10:00 PM): order.releaseTime defaults to 22:00 (store closing). Represents the official customer delivery cutoff on the target calendar day.
  • ML Prediction (07/07/26 07:42 AM): Adds the predicted duration ($1\text{ day} = 24\text{ hours}$) directly to intake time ($07:42\text{ AM} + 24\text{h}$). Represents the expected elapsed servicing completion time.

Finding: The two timestamps represent different operational concepts. Business Rules defines an end-of-business commitment deadline, while ML estimates elapsed workshop cycle time. They are not mathematically contradictory once these separate roles are recognized.

6. Claim Punctuality Reference Point VERIFIED FORMULA

In OrderDetailModal.tsx lines 2463-2478:

const expDt = authoritativeOfficialReleaseDate; // Business Rules target (07/07/26 10:00 PM) const claimDt = actualClaimedDate; // Customer pickup (07/06/26 03:45 PM) const expMid = new Date(expDt.getFullYear(), expDt.getMonth(), expDt.getDate()).getTime(); const claimMid = new Date(claimDt.getFullYear(), claimDt.getMonth(), claimDt.getDate()).getTime(); const diffDays = Math.round((claimMid - expMid) / (1000 * 60 * 60 * 24)); // -1 if (diffDays < 0) return "Claimed " + Math.abs(diffDays) + " day early";

Finding: Claim Punctuality compares claimed_at strictly against the Business Rules official promised date, not the ML prediction. Both timestamps are normalized to calendar-day midnight. Even though the elapsed clock difference is 30 hours and 15 minutes, the calendar-day difference is $-1$ day, yielding "Claimed 1 day early".

3. Academic Manuscript & Defense Alignment Statement

🎓 Capstone Defense Talking Point & Ground Truth Alignment

"The timestamps displayed on the Schedule & Tracking interface differ because they represent distinct, asynchronous events in the service lifecycle. Order Date records counter intake entry. Business Rules establishes the contractual customer delivery deadline ending at the store's daily closing cutoff (10:00 PM). ML Prediction estimates elapsed workshop turnaround duration projected from intake (7:42 AM). Actual Release Date records when workshop servicing concluded, while Claimed Date records customer pickup and final settlement. We maintain operational release and customer claim as separate data fields because workshop completion and customer retrieval are separate real-world events. In cases where an order is settled directly without a preceding status change, the backend records released_at = claimed_at as a fallback, which is explicitly tracked in our audit logs."
