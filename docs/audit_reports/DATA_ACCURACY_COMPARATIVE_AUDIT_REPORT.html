3. Audit Methodology & Rigorous Evaluation Criteria

To avoid subjective interpretations or false error counts, strict technical criteria were formulated prior to database inspection:

3.1 Criteria for Duplicate Transaction Records

A record is classified as a Duplicate if it satisfies either of the following conditions:

  • Technical Key Collision: Duplication of the unique tracking string (order_number) in the orders table.
  • Semantic Transaction Duplication: Multiple distinct order_id rows possessing identical customer_id, identical grand_total, identical shoe items/services, and an intake timestamp within the same calendar business day without distinct shoe pair physical tagging.

Enforcement Mechanism: In the digital system, duplicates are prevented at the database schema level via a UNIQUE CONSTRAINT on orders.order_number and customer auto-suggest matching in JobOrderForm.tsx.

3.2 Criteria for Incomplete Transaction Records

A record is classified as Incomplete if any required field necessary for full end-to-end transaction processing is missing (null, empty string, or unpopulated relational child table):

  • order_number: Unique alphanumeric order tracking tag.
  • customer_id & customer details: Non-empty customer name and valid 11-digit Philippine contact number.
  • status_id & priority_id: Valid foreign key references to lookup tables.
  • grand_total: Valid non-negative numerical billing total.
  • expected_at: Valid target release timestamp agreed upon with the customer.
  • created_at & user_id: Intake timestamp and processor user foreign key.
  • items relationship: Minimum of 1 active child record in the items table detailing shoe brand, model, and service mapping.
  • payments relationship: Minimum of 1 active child record in the payments table recording initial payment status, method, and balance.

3.3 Criteria for Data Corrections (Distinguishing Operational Workflow from Error Fixes)

A critical directive of this audit is: Do NOT count normal workflow/status changes as corrections. Operational status progression through the standard finite state machine:

New Order → On-Going (Inventory Allocation) → For Release → Claimed (Balance Settlement)

represents normal business operations, not erroneous data. Similarly, official cancellations with refund reasons, status undo operations authorized by policy, and automated UTC/local display timezone offsets are operational system events.

A transaction is classified as requiring Actual Data Correction ONLY when the system audit log records an intentional post-entry modification to repair an erroneous value, such as:

  • Correction of customer identification or contact details initially entered incorrectly.
  • Correction of shoe condition specifications or material tagging after workshop physical inspection.
  • Correction of erroneous pricing or accidental assignment of extraneous retail inventory items.
  • Manual correction of promised completion timestamps due to schedule adjustments.
