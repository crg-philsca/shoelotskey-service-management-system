B Measurement Definition: "Dashboard Report Generation Time"

Precision Scope

The evaluator specifically questioned what the reported dashboard generation times represent. This benchmark precisely establishes and standardizes the following definition:

Operational Definition of Measured Metric:

"DASHBOARD REPORT GENERATION TIME" is the end-to-end application-level response time measured using Python's hardware-backed monotonic microsecond timer (time.perf_counter()). It measures the complete request-response lifecycle:

  1. Request Dispatch: TestClient initiates an HTTP GET request to FastAPI endpoint (/api/reports/data) with specified report parameters.
  2. Authentication & RBAC Middleware: FastAPI verifies the session context, decodes claims, and validates user roles (owner / admin).
  3. Database Query Execution: SQLAlchemy executes cohort queries with relational joins (joinedload across orders, items, services, payments, expenses).
  4. Accounting Engine Calculation: report_service.py executes business logic to determine sales eligibility, collections, balance due, retained deposits, refunds, operating vs. inventory expenses, net profit, and ROI percentage.
  5. Payload Serialization & Return: Complete report payload (summary + itemized cohort details) is serialized to JSON and received by the client.

Explicit Boundary: This benchmark measures pure application/API report-generation response time and does NOT include browser visual rendering, DOM reflow/painting, user navigation, login time, or human interpretation time.

J Methodological & Interpretation Limitations

Academic Transparency

Six Essential Methodological Qualifications:

  1. Disparate Timing Modalities: The manual time represents human physical activity (manual retrieval of paper receipts, visual scanning of physical ledger books, mental/calculator addition, hand-written summary compilation). The dashboard benchmark measures machine application/API processing and response generation.
  2. Precise Technical Boundary: The benchmark measures application/API response time and explicitly does NOT include browser DOM rendering, graphical painting, user mouse navigation, login authentication, or user comprehension time.
  3. Workflow Stage Context: The comparison is intended to quantify operational efficiency gains specifically at the report-generation stage after transaction records have already been digitized in the database.
  4. Dataset & Schema Specificity: The results apply specifically to the tested 103-order Shoelotskey database, SQLite runtime environment, and tested reporting periods.
  5. Non-Universality: The findings demonstrate feasibility and system efficiency for Shoelotskey Villamor-Pasay and should not be construed as universal benchmarks for arbitrary enterprise databases or varied server hardware.
  6. Researcher-Observed Baseline: The manual reporting timings are human observation baselines from field study tests; software benchmarks measure the digital system only.
